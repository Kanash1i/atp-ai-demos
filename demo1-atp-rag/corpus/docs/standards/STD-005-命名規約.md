# STD-007 命名规约

制定日：2023-04-01 ／ 最终修订：2025-06-15 ／ 管理：QA 基盘团队

本篇规定 case_code、title、step description 三者的命名要求。命名不是形式主义 —— **case_code 是缺陷单、周报、执行报告之间唯一的关联键**，格式一乱，追溯链就断了。

## case_code 格式

### 规定（自动生成）

格式固定为：

```
ATP-{MODULE}-{4位序号}
```

- `ATP` 固定前缀，大写
- `{MODULE}` 取自模块字典的 `module_code`，大写，见《模块划分说明》
- `{4位序号}` 模块内递增，不足 4 位补零

示例：

```
✅ ATP-LOGIN-0001
✅ ATP-PAYMENT-0042
✅ ATP-ADMIN-0137
```

违反示例：

```
❌ ATP-LOGIN-1          序号未补齐 4 位
❌ atp-login-0001       未使用大写
❌ ATP-登录-0001         模块段必须用 module_code，不能用中文名
❌ LOGIN-0001           缺少 ATP 前缀
❌ ATP-LOGIN-0001-V2    不允许追加后缀
```

### 由平台生成，不允许手工填写

case_code 在案例创建时**由平台自动生成**，序号取该模块当前最大值加一。编辑界面上该字段是只读的。

这一点在 2024 年做了变更。此前允许手工填写，结果出现了重复编号、跳号、格式不一致等问题，缺陷单里引用的编号找不到对应案例的情况时有发生。改为自动生成后这类问题消失。

**历史遗留的不规范编号不做批量修正** —— 修改 case_code 会导致既有缺陷单和报告的引用失效，代价大于收益。

### 序号不回收

案例被删除或废弃后，其序号**不会被重新分配**。

这意味着模块内的序号会出现空洞，这是正常的。空洞比重用更安全：重用会让历史报告里的编号指向一条完全不同的案例，追溯时产生误导。

## title 写法

### 基本要求

title 是必填字段，上限 200 字符。要求一句话说清**测什么、在什么条件下、期望什么结果**。

推荐句式：

```
{条件}下{操作}，应{预期结果}
```

示例：

```
✅ 密码连续输错 5 次后登录，应提示账号被锁定
✅ 购物车含缺货商品时结算，应阻止提交并高亮缺货项
✅ 管理员导出超过 10 万行的报表，应转为异步任务并发送邮件通知
```

### 应避免的写法

```
❌ 测试登录                    没有信息量，看不出测什么
❌ 登录功能测试                 同上
❌ ATP-LOGIN-0001 的测试        用编号当标题，等于没写
❌ 验证登录页面各项功能是否正常     范围过大，说明这条案例测了太多东西
❌ bug#12345 的回归             依赖外部系统才能理解
```

最后两条尤其要注意。**如果一条案例的 title 写不出具体的预期结果，通常说明这条案例的测试意图本身就不清晰**，应该先想清楚再写，或者拆成多条。

### 语言使用

title 可以用中文或日文，**同一个项目内保持一致**即可，不强制统一语言。

但**不要中日混写**在同一个 title 里。检索和排序时会造成困扰。

## step description 要求

### 何时必填

`tc_step.description` 原则上是可选字段，但以下情况**必须填写**：

| 情况 | 理由 |
|---|---|
| `on_failure` 为 `CONTINUE` 或 `RETRY` | 需要说明为什么这一步允许失败 / 需要重试 |
| 使用了 `SWITCH_FRAME` / `SWITCH_WINDOW` | 需要说明切到哪里，否则后续步骤难以理解 |
| 定位器申请了 STD-002 例外 | 需要记录「已确认该 id 稳定」的根据 |
| 步骤的意图不能从 action 和定位器直接看出 | 见下 |

### 写什么

description 写**为什么**，不写**做什么**。

```
❌ 点击提交按钮              action 和定位器已经说明了，重复
✅ 此处提交会触发风控校验，可能弹出二次确认框，故 on_failure 设为 CONTINUE
```

「做什么」是从字段就能读出来的信息，重复一遍没有价值。「为什么」才是读案例的人需要而字段里没有的。

## 与自动检查的关系

| 项目 | 检查方式 |
|---|---|
| case_code 格式 | 平台自动生成，不存在违规可能 |
| title 非空、长度 | 保存时自动校验 |
| title 是否有信息量 | **无法机器判定**，评审时人工确认 |
| description 必填场景 | 保存时自动校验（按上表条件） |
| description 内容质量 | **无法机器判定**，评审时人工确认 |

两项「无法机器判定」的内容是评审的重点。自动校验通过不代表符合本规约。评审要点见《案例评审 checklist》。
