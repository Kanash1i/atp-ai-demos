# 案例评审 checklist

制定日：2023-06-01 ／ 最终修订：2025-10-05 ／ 管理：QA 基盘团队

本篇是案例提交前的自检清单和评审人的核对清单。**重点是那些机器检查不出来的项目** —— 平台的自动校验只能覆盖格式和硬性规则，判断质量的部分仍然需要人。

## 使用方式

### 提交前自检

作者在把案例状态从 `DRAFT` 改为 `ACTIVE` 之前，自己过一遍下面的清单。

### 评审

P0 / P1 案例**必须**经过评审，P2 / P3 建议评审。评审人不能是作者本人。

评审在案例详情页的评论区进行，通过后由评审人把状态改为 `ACTIVE`。

## 自动校验已覆盖的部分

以下项目由平台在保存时自动检查，**不需要人工核对**：

| 检查项 | 规范 | 级别 |
|---|---|---|
| XPath 绝对路径 | STD-001 | ERROR |
| XPath 动态 id | STD-002 | WARN |
| `SLEEP` 的使用 | STD-004 | ERROR |
| `CLICK` 的等待策略 | STD-005 | 自动补完 |
| `ASSERT_*` 的等待策略 | STD-006 | 自动补完 |
| case_code 格式 | STD-007 | 自动生成 |
| 至少一个断言 | STD-008 | ERROR |
| `seq` 连续性 | — | 自动维护 |
| 必填字段 | — | ERROR |

**自动校验通过 ≠ 案例合格。** 下面的部分才是评审的实质内容。

## 检查清单

### 一、测试意图

- [ ] **title 能看出测什么、期望什么结果**
      写不出具体预期，通常说明测试意图本身不清晰
- [ ] **一条案例只测一件事**
      title 里出现「和」「以及」「各项」往往是信号，考虑拆分
- [ ] **precondition 写清楚了**
      执行失败时排查的第一件事就是前置条件，写了能省很多时间
- [ ] **不与已有案例重复**
      同模块下搜一下关键词，重复覆盖是维护成本的常见来源

### 二、断言质量

- [ ] **断言的是业务结果，不是中间状态**
      `ASSERT_VISIBLE` 一个容器是最弱的断言
- [ ] **关键操作后有断言，失败能就近暴露**
      断言全堆在末尾，报错位置会离真正的问题很远
- [ ] **没有与测试意图无关的断言**
      判断标准：这条断言失败，是否意味着本案例要测的东西坏了
- [ ] **否定断言前有正向断言**
      页面没加载完时 `ASSERT_NOT_EXIST` 会假阳性通过
- [ ] **文案断言用部分匹配，断言的是稳定关键词**
      多语言站点尤其注意

详见《断言规范》。

### 三、定位器

- [ ] **没有绝对路径**（自动检查，但确认一下）
- [ ] **没有依赖自动生成的 id**，若有则 description 里记了「已确认稳定」的根据
- [ ] **没有用索引下标定位列表行**
      改成按内容定位，见《定位器指南》
- [ ] **class 用的是部分匹配而非完全相等**
- [ ] **链式定位没有超过必要的长度**
      每多一层就多一个会断的点

### 四、等待与容错

- [ ] **没有 `SLEEP`**（自动检查）
- [ ] **`on_failure` 不是 `ABORT` 的步骤，description 说明了理由**
- [ ] **没有滥用 `RETRY`**
      需要靠重试才稳定的步骤，先怀疑等待策略写错了
- [ ] **`wait_timeout_sec` 之和小于 `timeout_sec`，且留有余量**
      建议 1.5 倍以上
- [ ] **上传文件的步骤用 `PRESENCE` 而非 `VISIBLE`**
      `input[type=file]` 通常是隐藏的

### 五、可维护性

- [ ] **URL 用 `${base_url}` 而非硬编码**
      否则换环境就得改案例
- [ ] **密码用 `@cred{}` 而非明文**
- [ ] **数据集不超过 20 行**
      超了说明在穷举而不是选等价类
- [ ] **不依赖其他案例的执行结果**
      ATP 不支持案例间依赖，依赖了就无法单独重跑
- [ ] **测试数据不与其他案例共用**
      并发执行时会互相干扰，是偶发失败的常见来源

### 六、执行验证

- [ ] **单独执行通过至少一次**
- [ ] **连续执行 3 次都通过**
      只跑一次通过说明不了稳定性
- [ ] **确认失败时的报错能指向问题**
      故意改错一个定位器跑一次，看报错是否有意义（可选，但对 P0 案例推荐）

## 评审时的常见问题

### 「跑通了就行」

跑通只是最低要求。一条断言写错方向的案例也能跑通 —— 它只是永远不会失败而已。

评审时应该问：**这条案例在什么情况下会失败？** 如果答不上来，说明断言有问题。

### 「先合了再优化」

案例合进去之后就进入回归队列，不稳定的案例会持续产生噪音，而处理噪音的成本由整个团队承担。

**不稳定的案例不如没有案例。** 它消耗的排查时间通常远大于它发现的问题。

### 「历史案例都是这么写的」

历史案例中存在规范建立之前的写法（`SLEEP`、绝对路径、无断言等）。这些是待改造的技术债，不是可以参照的先例。

参照存量案例时，**先确认那条案例本身是否合规**。可以在案例列表页按「违规标记」筛选，带标记的不要参照。

## 评审记录

评审意见写在案例的评论区，不要私聊。原因：

1. 后续维护这条案例的人能看到当时的讨论
2. 同类问题可以沉淀成规范条目
3. 避免同一个问题在不同案例上被反复指出

如果一个问题在评审中反复出现三次以上，应该反馈给 QA 基盘团队，考虑加入自动校验或补进规范。**评审发现的共性问题应该变成机制，而不是靠每次评审去抓。**
