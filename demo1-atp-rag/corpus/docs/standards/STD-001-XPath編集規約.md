# STD-001〜003 XPath 編集規約

制定日：2023-04-01 ／ 最終改訂：2025-11-20 ／ 管理：QA 基盤チーム

本規約は ATP 上で作成するテストケースのロケータ記述について、**遵守義務のある基準**を定める。書き方の指針や使い分けについては《定位器指南》を参照のこと。本規約は判定基準そのものを規定する。

## 適用範囲と違反レベル

### 適用範囲

`tc_step.locator_type` が `XPATH` であるすべてのステップに適用する。`CSS` / `ID` / `NAME` / `LINK_TEXT` には STD-003 のみ適用する。

新規作成ケースは全項目必須。既存ケースは改修時に順次適用する（一括改修は行わない）。

### 違反レベルの定義

| レベル | 意味 | レビュー時の扱い |
|---|---|---|
| `ERROR` | 保存を許可しない | 修正するまでマージ不可 |
| `WARN` | 保存は可能だが記録に残る | レビューで指摘、原則修正 |
| `INFO` | 推奨事項 | 改善提案として伝える |

## STD-001 絶対パスの禁止（ERROR）

### 規定

ルート要素から数えた位置指定のみで構成されるパス、すなわち `/html` で始まるロケータの使用を**禁止する**。

```
❌ /html/body/div[2]/div[1]/form/div[3]/input
❌ /html/body/div/div/div/div/table/tbody/tr[1]/td[2]/a
```

### 禁止理由

絶対パスは DOM 構造の**全階層に依存する**。中間に要素が一つ挿入されただけで破綻するが、ラッパー要素の追加はフロントエンド改修において極めて頻度が高い。

さらに問題なのは、この破綻が**改修と同時には検知されない**点である。次回のリグレッション実行まで気づかれず、その時点では改修内容との関連が追いにくくなっている。

### 是正方法

安定した祖先要素を起点とし、`//` で中間階層を省略する。

```
✅ //form[@name="login"]//input[@name="username"]
✅ //div[@data-testid="order-table"]//a[contains(@class,"detail")]
```

起点として適切なのは、`data-testid` を持つ要素、意味のある `id` を持つ要素、`form` や `table` などの構造的に安定したタグである。

## STD-002 動的生成 ID への依存禁止（WARN）

### 規定

フレームワークまたはコンポーネントライブラリが**自動採番した識別子**をロケータに使用してはならない。

代表的な接頭辞：

| 接頭辞 | 由来 |
|---|---|
| `ext-gen`, `ext-comp` | Ext JS |
| `mat-input-`, `cdk-overlay-` | Angular Material |
| `el-id-`, `el-popper-` | Element UI |
| `:r0:`, `:r1:` | React `useId` |
| `uid-`, `auto-` | 各種内製フレームワーク |

```
❌ //*[@id="ext-gen1234"]
❌ //div[@id="mat-input-7"]//input
❌ //*[@id=":r3:"]
```

### 禁止理由

これらの識別子は**描画順に採番される**。画面上のコンポーネントが一つ増減しただけで全体がずれるため、無関係な改修によって破綻する。

`ERROR` ではなく `WARN` としているのは、稀に安定している実装が存在するため。ただし**安定していることを確認した根拠を `description` に記載すること**を条件とする。根拠の記載がない場合はレビューで差し戻す。

### 是正方法

同一要素を、周辺の安定要素からの相対位置で特定し直す。

```
✅ //label[text()="ユーザー名"]/following-sibling::input
✅ //div[@data-testid="login-form"]//input[@type="text"]
```

ラベルテキストからの相対指定は多言語対応時に破綻するため、`data-testid` の付与をフロントエンド担当へ依頼することを第一選択とする。

## STD-003 属性選択の優先順位（INFO）

### 規定

ロケータに使用する属性は、以下の優先順位に従うことを推奨する。

```
data-testid  >  name  >  id（人手命名のもの）  >  class  >  テキスト内容
```

### 各属性の評価

| 属性 | 安定性 | 備考 |
|---|---|---|
| `data-testid` | 最高 | テスト専用。改修時に変更されない前提で運用されている |
| `name` | 高 | バックエンドのパラメータ名と対応するため変更コストが高い |
| `id` | 中 | 人手命名なら安定。自動生成は STD-002 で禁止 |
| `class` | 低 | 見た目の変更で変わる |
| テキスト | 最低 | 文言変更・多言語切替で破綻 |

### class を使う場合

やむを得ず `class` を使用する場合は、**完全一致ではなく部分一致**とすること。

```
❌ //button[@class="btn btn-primary btn-lg"]
✅ //button[contains(@class,"btn-primary")]
```

クラス属性は複数値を持ち、順序も保証されない。完全一致は無関係なクラスの増減で破綻する。

### インデックス指定について

位置による指定は、**一覧の並び順が仕様上保証されている場合を除き**避けること。

```
❌ //table//tr[3]/td[2]
✅ //tr[td[text()="ORD-20250115-001"]]/td[@data-col="status"]
```

並び順はソート条件・データ件数・ページングによって変動する。内容による特定に置き換えること。

## 自動チェックとの関係

ATP の保存時チェックは STD-001 を `ERROR`、STD-002 を `WARN` として自動判定する。STD-003 は機械判定が難しいため**レビュー時の人手確認**に委ねる。

自動チェックを通過したことは本規約への適合を意味しない。特に STD-003 はチェック対象外であることに留意すること。

## 例外申請

被テストシステム側の制約により本規約に適合できない場合、QA 基盤チームへ例外申請を行うこと。申請時には以下を明記する：

1. 適合できない技術的理由
2. 代替案を検討した記録
3. 恒久対応の予定時期（フロントエンドへの `data-testid` 付与依頼など）

例外は**期限付きで承認**する。期限管理のない恒久的な例外は認めない。
