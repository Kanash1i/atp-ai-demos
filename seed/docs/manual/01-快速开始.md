# ATP 平台快速开始

本篇面向第一次使用 ATP 的测试工程师，用一条完整的登录测试案例走完「建案例 → 加步骤 → 执行 → 看报告」全流程。

预计耗时 20 分钟。读完本篇后建议接着读《案例结构》和《定位器指南》。

## 登录与权限

### 账号获取

ATP 使用公司统一域账号登录，不需要单独注册。首次登录后系统会自动创建个人工作区。

如果登录后提示「没有可访问的项目」，说明域账号还没有被加入任何项目组。找所在项目的 QA 负责人在「管理画面 → 成员管理」里添加即可，权限生效不需要重新登录，刷新页面就行。

### 三种角色

ATP 的权限模型只有三种角色，粒度到项目级别：

| 角色 | 能做什么 | 典型使用者 |
|---|---|---|
| `VIEWER` | 只能查看案例和报告，不能改 | 开发、PM |
| `EDITOR` | 创建 / 编辑 / 执行案例 | 测试工程师 |
| `OWNER` | 在 EDITOR 基础上，可管理成员、删除案例、修改项目配置 | QA 负责人 |

注意 `EDITOR` **不能删除案例**，只能把状态改成 `DEPRECATED`。这是刻意设计的，因为案例被删掉之后历史执行报告会失去关联，排查线上问题时会断线索。

## 创建第一条案例

### 填写案例基本信息

进入「案例管理 → 新建案例」，需要填的字段只有五个是必填的：

- **case_code** — 业务编号，格式必须是 `ATP-{模块}-{4位序号}`，例如 `ATP-LOGIN-0001`。详细规则见《命名規約》
- **title** — 一句话说清测什么，避免「测试登录」这种没有信息量的写法
- **module** — 从 8 个固定模块里选，决定了 case_code 的前缀
- **priority** — P0 到 P3，P0 是冒烟用例，每次发版必跑
- **author** — 默认填当前登录人，一般不用改

`precondition`（前置条件）不是必填，但强烈建议写。执行失败时排查的第一件事就是看前置条件是否满足，写了能省很多时间。

### 新建案例默认是草稿

新建的案例 `status` 默认是 `DRAFT`，**草稿状态的案例不会被批量执行任务捡起来**。

这一点新人经常踩：案例写完了、单独执行也通过，但加到回归任务里就是不跑。原因就是忘了把状态从 `DRAFT` 改成 `ACTIVE`。

状态一共三种：`DRAFT`（草稿，不参与批量执行）、`ACTIVE`（生效）、`DEPRECATED`（废弃，保留历史报告但不再执行）。

## 添加步骤

### 步骤的基本构成

一条案例由若干个**步骤**组成，每个步骤描述一个动作。步骤按 `seq` 从 1 开始顺序执行，中间不允许跳号。

一个最小的登录案例大致是这样：

| seq | action | 说明 |
|---|---|---|
| 1 | `OPEN_URL` | 打开登录页 |
| 2 | `INPUT` | 输入用户名 |
| 3 | `INPUT` | 输入密码 |
| 4 | `CLICK` | 点击登录按钮 |
| 5 | `ASSERT_VISIBLE` | 断言首页元素出现 |

每个 action 需要填哪些字段是不一样的，比如 `OPEN_URL` 不需要定位器，`CLICK` 需要定位器但不需要输入数据。完整对照表见《Action 参考》。

### 每条案例至少要有一个断言

上表第 5 步不是可选的。**没有断言的案例，执行「成功」不代表功能是好的** —— 它只证明了那几个点击操作没报错。

平台在保存时会做校验，没有任何 `ASSERT_*` 步骤的案例无法保存为 `ACTIVE` 状态。详见《断言规范》。

## 执行与查看结果

### 单条执行与批量执行

单条执行点案例详情页的「执行」按钮，会立刻分配一个执行器，一般几秒内开始跑。适合边写边调。

批量执行走「执行任务」，可以按模块、按优先级、按标签筛选一批案例，排队执行。回归测试用这个。

### 报告怎么看

执行完成后进报告页。排查失败时按这个顺序看，能少走弯路：

1. **先看失败步骤的截图** —— ATP 在每个步骤失败时自动截图，八成的问题看一眼截图就明白了（页面没加载完、弹了个意料之外的对话框、元素被遮挡）
2. **再看失败原因分类** —— 平台把失败分成 `ELEMENT_NOT_FOUND` / `TIMEOUT` / `ASSERT_FAILED` / `SCRIPT_ERROR` 四类，分类不同排查方向完全不同
3. **最后才看完整日志** —— 日志量大，前两步定位不到再看

如果失败原因是 `ELEMENT_NOT_FOUND` 或 `TIMEOUT`，多半不是被测系统的 bug，而是案例本身的定位器或等待策略有问题。具体排查步骤见《トラブルシューティング》。
