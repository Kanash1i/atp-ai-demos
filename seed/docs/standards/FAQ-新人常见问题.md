# FAQ — 新人常见问题

QA 基盘团队整理，按提问频率排序。中日混排（提问者用什么语言问的就用什么语言记录）。

最终更新：2025-12-18

## 平台能力

### Q1. ATP 支持 App（移动端）自动化吗？

**不支持。** ATP 只驱动桌面浏览器（Chrome / Firefox / Edge），没有任何移动端能力 —— 既不支持原生 App，也不支持真机上的移动浏览器。

移动端的自动化需求请联系移动开发团队，他们有独立的工具链。ATP 这边不做，也没有排期计划。

手机 Web 页面的验证，可以通过浏览器的响应式模式做近似验证，但这**不等于**真机测试。

### Q2. API / 接口测试できますか？

**できません。** ATP は Web UI 専用で、HTTP リクエストを直接送る機能はありません。JSON レスポンスを検証する仕組みもありません。

API テストは別のツールを使ってください。UI ケースの中で「ついでに」API を叩くこともできません。

### Q3. 数据库里的数据能直接断言吗？

不能。ATP 没有数据库连接能力，所有验证都必须通过页面上能看到的内容。

需要验证落库结果时，走管理后台的查询界面来看。如果后台没有对应的查询功能，这本身就值得提给产品 —— 测不了的东西通常也运维不了。

### Q4. 自分で JavaScript を書いて実行できますか？

できません。任意スクリプトの実行はサポートしていません。

これは意図的な制約です。スクリプトを許すと、ケースが「プログラム」になり、書ける人にしかメンテナンスできなくなります。ATP の利用者はコードを書かないテストエンジニアであるため、この制約は外しません。

### Q5. 画面のスクリーンショット比較（ビジュアルリグレッション）はできますか？

**できません。** 画像比較の機能はありません。

失敗時のスクリーンショットは記録されますが、それは調査用であって、比較の判定材料ではありません。

## 案例编写

### Q6. Action 一覧に無いアクションを使いたい

Action は 13 個で固定されており、**拡張できません**。一覧は《Action 参考》を参照してください。

もし他所で見かけたアクション名が一覧に無い場合、それは ATP のものではありません（別ツールの記法か、記憶違いの可能性が高い）。

必要な操作が本当に表現できない場合は QA 基盤チームへ相談してください。ただし過去の相談の大半は、既存 Action の組み合わせで解決しています。

### Q7. 案例保存时提示「至少需要一个断言步骤」

这是 STD-008 的硬性要求，没有例外。加一个 `ASSERT_*` 步骤即可。

如果实在想不出该断言什么，说明这条案例的测试意图不清晰 —— 先想清楚「这条案例失败时应该是什么情况」，答案通常就是该断言的东西。

### Q8. 「クリックしたのに次のステップで要素が見つからない」

多いのは次の 3 パターンです：

1. **新しいウィンドウ / タブが開いた** → `SWITCH_WINDOW` が必要
2. **iframe の中に入った** → `SWITCH_FRAME` が必要
3. **クリックが実際には効いていない** → 待機戦略が `CLICKABLE` になっているか確認

3 番目は「クリック成功」と記録されるため気づきにくいです。詳細は《トラブルシューティング》。

### Q9. 为什么我的案例在批量任务里不执行？

九成是 `status` 还停在 `DRAFT`。批量执行只捡 `ACTIVE` 状态的案例。

新建案例默认就是 `DRAFT`，写完记得改状态。P0 / P1 案例还需要评审通过后由评审人改。

### Q10. case_code を自分で決めたい

できません。case_code はプラットフォームが自動採番します（`ATP-{MODULE}-{4桁}`）。

以前は手入力可能でしたが、重複・欠番・書式不統一が多発したため 2024 年に自動生成へ変更しました。詳細は《命名规约》。

### Q11. 一条案例最多能有多少步骤？

没有硬性上限，但**超过 20 步就应该考虑拆分了**。

步骤多意味着：执行时间长、失败时定位困难、任何一步不稳整条就不稳。而且案例超时上限是 300 秒，步骤太多容易撞上限。

## 执行与排查

### Q12. ローカルでは通るのに CI で落ちる

ほぼ確実にタイミングの問題です。CI 環境は並列実行で負荷が高く、要素の準備が遅れます。

**タイムアウトを延ばすのは正しい対処ではありません。** まず `CLICK` の待機戦略が `CLICKABLE` になっているかを確認してください。詳細は《待機戦略規約》。

### Q13. 偶尔失败，重跑就好，要不要管？

要管。**不稳定的案例不如没有案例** —— 它消耗的排查时间通常远大于它发现的问题。

排查方向按可能性排序：等待策略写错 → 案例间数据冲突 → 测试数据被污染 → 被测系统确实不稳定。

最后一种经常被忽略。自动化发现的偶发问题，往往对应真实用户偶尔遇到的故障，值得报 bug 而不是改案例迁就。

### Q14. `ASSERT_FAILED` が出たらまずケースを直すべき？

いいえ。**`ASSERT_FAILED` は他の失敗分類と性質が異なります。**

`ELEMENT_NOT_FOUND` や `TIMEOUT` はケース側の不備であることが多いのに対し、`ASSERT_FAILED` は「要素は見つかり、見えているが、内容が期待と違う」状態です。これは被テストシステムの不具合を捉えている可能性が高い。

期待値が正しいかを必ず先に確認してください。

### Q15. Firefox で実行すると待ち時間が長い

Grid 内の Firefox / Edge ノードは Chrome より大幅に少ないため、順番待ちが発生します。

ブラウザ互換性の検証が目的でなければ、既定の Chrome のままにしてください。

## 规范与评审

### Q16. 历史案例里有 `SLEEP`，我照着写可以吗？

不可以。那些是规范建立之前的遗留，属于待改造的技术债，不是可参照的先例。

参照存量案例前，先确认那条案例本身是否合规 —— 案例列表页可以按「违规标记」筛选，带标记的不要参照。

### Q17. `SLEEP` を消したら不安定になった

`SLEEP` を消すだけでなく、**待機戦略を直す**必要があります。多くの場合、`CLICK` が `VISIBLE` になっているのが真因です。

そもそも `SLEEP` はその真因を時間差で覆い隠していただけなので、消せば元の問題が表面化します。詳細は《待機戦略規約》STD-004。

### Q18. 動的 ID をどうしても使いたい場合は？

STD-002 は `WARN` レベルなので保存自体は可能ですが、**`description` に「その ID が安定していることを確認した根拠」を書いてください**。根拠が無い場合はレビューで差し戻されます。

まずはフロントエンド担当に `data-testid` の付与を依頼するのが第一選択です。

### Q19. 评审要多久？P2 案例也要评审吗？

P0 / P1 必须评审，P2 / P3 建议评审但不强制。

评审通常 1 个工作日内完成。超过 2 天没有回应可以直接找 QA 负责人。

### Q20. 规范太多记不住

不需要全记。**硬性规则平台会自动拦你**（绝对路径、`SLEEP`、无断言这三条是 ERROR，保存不了）。

真正需要记的只有机器判断不了的部分，集中在《案例评审 checklist》里 —— 断言是否对应业务结果、失败能否就近暴露、有没有和测试意图无关的断言。

其余的遇到再查。规范的作用是提供判断依据，不是让人背诵。
